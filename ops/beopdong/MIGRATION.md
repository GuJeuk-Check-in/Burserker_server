# 법동 DB 변경 적용

이 문서는 적용 절차다. 저장소에 SQL을 추가하는 것만으로 실행 중인 DB가 바뀌지는 않는다.
구즉 마이그레이션을 사용하지 않으며, 실제 DB 변경은 백업·대상 확인 후 별도 작업한다.

## 변경 파일

- V1: 법동 기존 기본 테이블 5개(organ, user, log, purpose, purpose_log).
- V2: 방문 선택, 실제 이용 회차, 참가자를 분리하고 완료 이력과 연결한다.
- Hibernate ddl-auto는 none으로 유지한다. 앱 기동 시 Flyway가 미적용 버전을 실행한다.
- clean은 비활성화한다. 운영 DB에서 clean이나 볼륨 삭제를 사용하지 않는다.

## 적용 전

1. 대상이 법동인지 확인한다. 서버 DB는 beopdong_stag 또는 beopdong_prod, 로컬은 BeopDong이다.
2. 기존 앱의 쓰기를 중단하고, DB dump와 테이블 구조를 저장한다. dump에는 개인정보가 있으므로 커밋하지 않는다.
3. 기존 DB는 SHOW TABLES와 각 테이블의 SHOW CREATE TABLE로 V1의 기본 컬럼·관계가 있는지 확인한다.
   신청서 추가 필드(name, seat, use_purpose, count, start_at, end_at)는 없어도 V2가 추가한다.
   user.birthymd 등 기본 컬럼이 다르거나 일부 테이블만 있으면 먼저 구조를 확인한다. 무조건 baseline하지 않는다.
4. 진행 중인 노래방·탁구 다인 신청이 있으면 종료까지 기다린다. 과거 count만으로 동반자 신원을 알 수 없다.
5. Flyway 실행 계정에 테이블 생성·변경·조회·쓰기와 CREATE ROUTINE, ALTER ROUTINE, EXECUTE 권한이 필요하다.
   V2는 MySQL 8의 기존 컬럼 유무를 확인하는 일회성 프로시저를 사용하고 성공 후 제거한다.

## 비어 있는 DB

1. Flyway baseline-on-migrate=false(기본값)를 유지한다.
2. 수정 앱을 대상 DB로 기동하면 V1, V2 순서로 적용된다.
3. 기관 로그인 계정과 시설 기본값은 별도 안전한 초기 설정으로 준비한다. 마이그레이션에 비밀번호를 넣지 않는다.
   빈 DB에는 기관이 없으므로 휴식도 아직 없다. 기관 준비 후 휴식 목적을 반드시 만들고 locked=true로 설정한다.

## 테이블과 데이터가 있는 기존 DB

1. 위 구조 확인·백업을 마친 경우에만 baseline version 1을 사용한다.
2. 최초 기동 한 번에만 Spring 설정 SPRING_FLYWAY_BASELINE_ON_MIGRATE=true를 전달한다.
   앱이 기존 구조를 version 1로 등록하고 V2를 적용한다. 기본 application.yml의 false는 변경하지 않는다.
3. 적용 후 해당 임시 환경변수를 제거한다. 이후 기동에서는 기존 이력에 따라 새 버전만 적용된다.
4. baseline은 검증·변환 도구가 아니다. 다른 구조를 version 1로 등록해도 자동으로 맞춰주지 않는다.

## 기존 데이터 처리

- NONE: 선택 목록으로 복사하고 원본 행은 남긴다. 이전 log_purpose 테이블이 있으면 NONE 선택도 함께 복사하며 원본은 삭제하지 않는다. log_purpose에 시작된 기록이 있으면 시간 정보 없이 추정하지 않고 중단한다.
- PENDING: 이용 회차와 확인 가능한 신청자를 복사한다. 종료 시각이 지났으면 기존 행을 SUCCESS로 완료한다.
- 아직 사용 중인 PENDING 원본은 보존하고, 새 회차가 끝나면 종료 서비스가 새 완료 이력을 생성한다.
- SUCCESS: PK, 관리자 수정 이름, 기존 인원수, 좌석·시간·사용목적을 보존하고 회차를 연결한다.
- 모든 방명록에 기본 휴식을 연결한다. 예전 코드가 저장하지 않은 일반 목적 선택은 복구할 수 없다.
- 옛 다인 기록은 전체 인원수를 보존하지만 동반자 신원은 만들지 않는다. 해당 기록으로 개인별 인원 명단을 추정하지 않는다.
- 하나의 기관을 전제로 한다. 기관이 여러 개거나 새 회차 테이블이 이미 있으면 자동 이전을 중단한다.
- 활성 시설 중복, 활성 회원 중복, 시작·종료 시각 누락이 있어도 중단한다. 원본을 확인하고 처리해야 한다.

## 적용 확인

flyway_schema_history의 version 1, 2가 성공했는지 확인한다. 기존 DB의 version 1은 BASELINE으로 표시된다.
purpose_usage, purpose_usage_member, visit_purpose와 purpose_log.purpose_usage_id가 있어야 한다.
기존 회원·방명록 건수와 완료 기록의 PK·이름·인원수가 유지되는지 대조한다.
진행 중 신청을 조회한 뒤 종료 처리 시 한 회차에 완료 기록이 하나만 생기는지 확인한다.

## 실패한 경우

MySQL DDL은 일부 변경이 자동 커밋되어 전체 롤백되지 않을 수 있다.
실패했는데 이력만 repair하거나 재실행하지 않는다. 앱 쓰기를 막은 상태에서 오류·현재 구조를 확인한다.
적용 전 백업을 별도 DB에 복원하여 검증한 후 복구 대상을 정한다. 운영 DB를 덮어쓰는 복원은 별도 승인을 받는다.
롤백이 필요하면 DB 구조와 앱 이미지를 함께 고려한다. 오래된 앱만 다시 띄우는 것은 안전한 데이터 롤백이 아니다.


## 2026-11-11 검증 기록

기존 로컬 DB와 다른 데이터 폴더·포트의 임시 MySQL 8.0에서 검증했다. 서버에는 적용하지 않았다.

- 빈 DB의 V1/V2 적용, checksum 검증과 재실행 시 미적용 SQL 0건.
- 신청서 컬럼이 없던 초기 구조와 이미 컬럼이 있는 구조의 기존 DB baseline 및 V2 적용.
- 회원·방명록·원본 신청서 건수, 완료 신청서 PK·수정 이름·인원수 보존.
- NONE 선택 목록, 기본 휴식, 활성 단일 이용, 종료된 다인 이력 이전 및 중복 이력 제약.
- 활성 다인 신청, 잘못된 시작·종료 시각, 동일 회원의 활성 중복 이용은 이전 중단.
- 마이그레이션 후 실제 Spring Boot 기동 및 Hibernate validate 통과.
- 실제 MySQL 트랜잭션에서 노래방 마지막 자리·컴퓨터 같은 좌석의 동시 신청은 각 한 건만 성공.
- 참가자 모두 저장, 노래방 첫 시작부터 30분, 회차별 완료 이력 한 건, 같은 날 재이용 확인.

검증용 프로그램은 작업 폴더에만 두었으며 저장소에 테스트 파일이나 H2 의존성을 추가하지 않았다.
기존 로컬 DB·Redis 연결 테스트는 Flyway를 비활성화하여 연결 확인이 스키마 변경을 일으키지 않게 했다.


## 로컬 실제 적용 기록

2026-11-11 사용자 승인으로 localhost:3306/BeopDong에 적용했다. 스테이징·운영 DB는 변경하지 않았다.
저장소 밖 C:/env/backups/beopdong에 전체·구조 백업을 만들고 완료 표시와 SHA-256을 확인했다.
원본 기본 구조를 확인하여 version 1로 baseline한 뒤 V2를 적용했고, 재검증 및 Hibernate validate가 통과했다.

| 항목 | 적용 전 | 적용 후 |
|---|---:|---:|
| 회원 | 15 | 15 |
| 방명록 | 15 | 15 |
| 기관 | 1 | 1 |
| 목적 종류 | 10 | 11 (기본 휴식 추가) |
| 기존 purpose_log | 29 | 29 |
| 옛 log_purpose | 4 | 4 |

방문 선택 48건, 이용 회차·참가자 각 9건을 만들었다. 회원·방명록·기관·옛 선택 원본과
기존 신청서의 ID·인원·좌석·시간 등 보존 대상 값은 이전 전후 해시로 대조했다.
옛 log_purpose의 NONE 선택 4건도 누락 없이 복사했다. 실행 중인 법동 앱은 없었다.

V1/V2는 이 로컬 DB에 적용된 버전이다. 이후 SQL 수정이 필요하면 적용된 파일을 고치지 말고 V3 이상을 추가한다.
